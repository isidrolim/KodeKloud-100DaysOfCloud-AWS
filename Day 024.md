# 100 Days of Cloud AWS - Day 024: Setting Up an Application Load Balancer for an EC2 Instance

## Scenario

The Nautilus DevOps team is preparing a simple application architecture in AWS.

An Nginx web server is already running on an existing EC2 instance. Instead of exposing the application directly, an **Application Load Balancer (ALB)** must be placed in front of the EC2 instance so incoming HTTP traffic can be routed through the load balancer.

## Requirement

Configure the following resources:

- **Application Load Balancer:** `nautilus-alb`
- **Target Group:** `nautilus-tg`
- **ALB Security Group:** `nautilus-sg`
- **Public Listener:** HTTP port `80`
- **Backend Port:** HTTP port `80`
- **Target EC2 Instance:** `nautilus-ec2`
- **Region:** `us-east-1`
- Modify the EC2 instance's existing/default security group if necessary.

The final traffic path should be:

```text
Internet
   │
   │ HTTP :80
   ▼
nautilus-alb
   │
   │ HTTP :80
   ▼
nautilus-tg
   │
   │ HTTP :80
   ▼
nautilus-ec2
   │
   ▼
Nginx
```

## Implementation

### Step 1: Verify the Existing EC2 Instance

Open:

```text
EC2 → Instances
```

Locate:

```text
nautilus-ec2
```

Verify that:

- The instance is running.
- Nginx is already installed and running.
- Note the instance's VPC.
- Note the instance's Availability Zone/subnet.
- Note the security group currently attached to the instance.

The ALB and target group must be configured within the appropriate VPC.

### Step 2: Create the ALB Security Group

Navigate to:

```text
EC2 → Network & Security → Security Groups
```

Click:

```text
Create security group
```

Configure:

```text
Security group name: nautilus-sg
VPC:                 Same VPC as nautilus-ec2
```

Add the following inbound rule:

```text
Type:       HTTP
Protocol:   TCP
Port:       80
Source:     0.0.0.0/0
```

This allows public HTTP traffic to reach the Application Load Balancer.

Create the security group.

### Step 3: Create the Target Group

Navigate to:

```text
EC2 → Load Balancing → Target Groups
```

Click:

```text
Create target group
```

Select:

```text
Target type: Instances
```

Configure:

```text
Target group name: nautilus-tg
Protocol:          HTTP
Port:              80
VPC:               Same VPC as nautilus-ec2
```

Keep the HTTP health check configured for the application.

Continue to the target registration page.

### Step 4: Register the EC2 Instance

Under **Available instances**, select:

```text
nautilus-ec2
```

Configure the target port as:

```text
80
```

Click:

```text
Include as pending below
```

Confirm that `nautilus-ec2` appears under the registered targets and create the target group.

The backend relationship is now:

```text
nautilus-tg
     │
     │ HTTP :80
     ▼
nautilus-ec2
     │
     ▼
Nginx :80
```

### Step 5: Allow ALB Traffic to Reach the EC2 Instance

Navigate to the security group currently attached to:

```text
nautilus-ec2
```

Edit its inbound rules if necessary.

Allow HTTP traffic on port `80` from the ALB security group:

```text
Type:    HTTP
Port:    80
Source:  nautilus-sg
```

Using the ALB security group as the source is preferable to opening the EC2 instance itself directly to:

```text
0.0.0.0/0
```

The security relationship becomes:

```text
Internet
   │
   │ :80
   ▼
nautilus-sg
   │
   ▼
Application Load Balancer
   │
   │ :80
   ▼
EC2 Security Group
Source = nautilus-sg
   │
   ▼
nautilus-ec2
```

### Step 6: Create the Application Load Balancer

Navigate to:

```text
EC2 → Load Balancing → Load Balancers
```

Click:

```text
Create load balancer
```

Select:

```text
Application Load Balancer
```

Configure:

```text
Load balancer name: nautilus-alb
Scheme:             Internet-facing
IP address type:    IPv4
```

Under **Network mapping**:

- Select the same VPC as `nautilus-ec2`.
- Select the required Availability Zones/subnets for the ALB.

> An Application Load Balancer requires subnets from at least two Availability Zones.

### Step 7: Attach the Security Group

Under **Security groups**, select:

```text
nautilus-sg
```

Remove other security groups if they are not required by the challenge.

### Step 8: Configure the Listener

Configure the listener:

```text
Protocol: HTTP
Port:     80
```

For the default action, select:

```text
Forward to → nautilus-tg
```

The forwarding configuration should now be:

```text
ALB Listener
HTTP :80
   │
   ▼
nautilus-tg
HTTP :80
   │
   ▼
nautilus-ec2
HTTP :80
```

Review the configuration and click:

```text
Create load balancer
```

## Validation

### Validate the Target Group

Navigate to:

```text
EC2 → Target Groups → nautilus-tg → Targets
```

Wait for the target health to become:

```text
Healthy
```

Expected:

```text
Target:  nautilus-ec2
Port:    80
Health:  Healthy
```

Do not consider the deployment complete while the target remains unhealthy.

### Validate the Load Balancer

Navigate to:

```text
EC2 → Load Balancers → nautilus-alb
```

Verify:

```text
Name:     nautilus-alb
Scheme:   Internet-facing
State:    Active
Listener: HTTP :80
```

Verify that the listener forwards to:

```text
nautilus-tg
```

### Validate End-to-End Connectivity

Copy the ALB DNS name from the load balancer details.

Open it in a browser:

```text
http://<ALB-DNS-NAME>
```

The Nginx sample page should load successfully.

The complete dependency path is now:

```text
Client
  │
  │ HTTP :80
  ▼
Internet
  │
  ▼
nautilus-alb
  │
  │ nautilus-sg
  ▼
Listener :80
  │
  ▼
nautilus-tg
  │
  │ Target Health Check
  ▼
nautilus-ec2 :80
  │
  ▼
Nginx
  │
  ▼
Sample Web Page
```

✅ Public HTTP port `80` allowed to the ALB.

✅ Target group `nautilus-tg` created.

✅ `nautilus-ec2` registered as a target on port `80`.

✅ EC2 security group configured to permit required ALB traffic.

✅ Application Load Balancer `nautilus-alb` created.

✅ HTTP listener configured on port `80`.

✅ Listener forwards requests to `nautilus-tg`.

✅ Target health verified as `Healthy`.

✅ Nginx application reachable through the ALB.

✅ Challenge successfully completed and validated.

## Key Takeaway

An Application Load Balancer introduces several dependencies between the client and the application:

```text
Client
  ↓
ALB Security Group
  ↓
ALB Listener
  ↓
Listener Rule
  ↓
Target Group
  ↓
EC2 Security Group
  ↓
EC2 Instance
  ↓
Application
```

A load balancer being `Active` does **not** automatically mean the application is working.

One of the most important validation points is:

```text
Target Health = Healthy
```

If the target is unhealthy, troubleshoot the dependency path systematically:

```text
Is Nginx running?
      ↓
Is it listening on port 80?
      ↓
Does the EC2 security group allow traffic from the ALB?
      ↓
Is the target registered on the correct port?
      ↓
Is the health check path valid?
      ↓
Is the target Healthy?
      ↓
Does the ALB listener forward to the correct target group?
```

For production environments, allowing the EC2 instance to receive HTTP traffic specifically from the **ALB security group** instead of directly from the entire internet creates a cleaner security boundary:

```text
Internet → ALB → EC2
```

rather than:

```text
Internet ──────────→ EC2
     └──→ ALB ────→ EC2
```

This keeps the load balancer as the intended public entry point to the application.
