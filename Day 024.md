# 100 Days of Cloud AWS - Day 024: Setting Up an Application Load Balancer for an EC2 Instance

## Scenario

The Nautilus DevOps team needed to place an **Application Load Balancer (ALB)** in front of an existing EC2 instance running Nginx.

The goal was to expose the application through the ALB on HTTP port `80` while forwarding traffic to the backend EC2 instance on port `80`.

## Requirement

Configure the following AWS resources:

- **Application Load Balancer:** `nautilus-alb`
- **Target Group:** `nautilus-tg`
- **ALB Security Group:** `nautilus-sg`
- **Frontend Listener:** HTTP port `80`
- **Backend Port:** HTTP port `80`
- **EC2 Instance:** `nautilus-ec2`
- **Region:** `us-east-1`

The existing default security group attached to the EC2 instance also needed to be updated to allow traffic from the ALB.

## Initial State

The existing EC2 instance was verified first.

```text
Instance:     nautilus-ec2
State:        Running
Instance Type: t2.micro
Private IP:   172.31.36.27
VPC:          vpc-063a006a0a507d135
Security SG:  default
```

The default EC2 security group initially allowed traffic only from itself.

## Implementation

### Step 1: Create the ALB Security Group

Navigate to:

```text
EC2 → Network & Security → Security Groups
```

Create:

```text
Security Group Name: nautilus-sg
VPC:                 Same VPC as nautilus-ec2
```

Configure the inbound rule:

```text
Type:     HTTP
Protocol: TCP
Port:     80
Source:   0.0.0.0/0
```

This allows public HTTP traffic to reach the Application Load Balancer.

### Step 2: Allow ALB Traffic to Reach the EC2 Instance

Open the **default security group** attached to `nautilus-ec2`.

Add the following inbound rule:

```text
Type:     HTTP
Protocol: TCP
Port:     80
Source:   nautilus-sg
```

The important security relationship became:

```text
Internet
   │
   │ HTTP :80
   ▼
nautilus-sg
   │
   ▼
Application Load Balancer
   │
   │ HTTP :80
   ▼
EC2 default security group
Source = nautilus-sg
   │
   ▼
nautilus-ec2
```

This avoids exposing the EC2 instance directly to the internet on port `80`.

### Step 3: Create the Target Group

Navigate to:

```text
EC2 → Load Balancing → Target Groups
```

Create a target group with:

```text
Target type:        Instances
Target group name:  nautilus-tg
Protocol:           HTTP
Port:               80
Protocol version:   HTTP1
VPC:                Same VPC as nautilus-ec2
```

Health check configuration:

```text
Protocol: HTTP
Port:     Traffic port
Path:     /
```

### Step 4: Register the EC2 Instance

Under **Register targets**, select:

```text
nautilus-ec2
```

Configure:

```text
Port: 80
```

Click:

```text
Include as pending below
```

Then create the target group.

The backend relationship became:

```text
nautilus-tg
     │
     │ HTTP :80
     ▼
nautilus-ec2
```

### Step 5: Create the Application Load Balancer

Navigate to:

```text
EC2 → Load Balancing → Load Balancers
```

Create an **Application Load Balancer**.

Configure:

```text
Load balancer name: nautilus-alb
Scheme:             Internet-facing
IP address type:    IPv4
VPC:                Same VPC as nautilus-ec2
```

### Step 6: Select Multiple Availability Zones

An Application Load Balancer requires subnets in at least **two Availability Zones**.

The EC2 instance was located in:

```text
us-east-1c
```

The ALB was configured with subnets in two Availability Zones:

```text
us-east-1c
+
us-east-1a
```

This allows AWS to deploy load balancer nodes across multiple Availability Zones.

### Step 7: Attach the ALB Security Group

Under **Security groups**, select:

```text
nautilus-sg
```

This security group allows:

```text
HTTP :80 from 0.0.0.0/0
```

### Step 8: Configure the Listener

Configure the listener:

```text
Protocol: HTTP
Port:     80
```

Set the default action to:

```text
Forward to → nautilus-tg
```

The complete forwarding path became:

```text
Client
  │
  │ HTTP :80
  ▼
nautilus-alb
  │
  ▼
Listener HTTP :80
  │
  ▼
nautilus-tg
  │
  │ HTTP :80
  ▼
nautilus-ec2
  │
  ▼
Nginx
```

## Validation

### Validate the Load Balancer

Navigate to:

```text
EC2 → Load Balancers → nautilus-alb
```

Verify:

```text
Load Balancer: nautilus-alb
Type:          Application
Scheme:        Internet-facing
State:         Active
Listener:      HTTP :80
```

Confirm that the listener forwards to:

```text
nautilus-tg
```

### Validate the Target Group

Navigate to:

```text
EC2 → Target Groups → nautilus-tg → Targets
```

Verify:

```text
Target:        nautilus-ec2
Port:          80
Health Status: Healthy
```

The **Healthy** target status proved that the ALB could successfully reach Nginx through the configured network path.

### Validate the Application

Copy the ALB DNS name and open it in a browser:

```text
http://<ALB-DNS-NAME>
```

The Nginx sample page loaded successfully.

Final dependency path:

```text
Internet
   │
   │ HTTP :80
   ▼
nautilus-alb
   │
   │ nautilus-sg
   ▼
Listener :80
   │
   ▼
nautilus-tg
   │
   │ Healthy
   ▼
nautilus-ec2 :80
   │
   ▼
Nginx
   │
   ▼
Web Page
```

## Key Takeaway

An Application Load Balancer depends on several components working together:

```text
Client
  ↓
ALB Security Group
  ↓
ALB Listener
  ↓
Target Group
  ↓
EC2 Security Group
  ↓
EC2 Instance
  ↓
Application
```

The most important health indicator is:

```text
Target Health = Healthy
```

A load balancer showing `Active` does not automatically prove that the backend application is reachable.

The target group health check validates the backend path:

```text
ALB
 ↓
Security Group
 ↓
Target Group
 ↓
EC2 :80
 ↓
Nginx
```

Another important design lesson is that the backend EC2 instance does not need to be directly exposed to the internet.

Instead of:

```text
Internet → EC2 :80
```

the safer architecture is:

```text
Internet → ALB :80
              ↓
           EC2 :80
```

The EC2 security group can trust the ALB security group specifically:

```text
Source: nautilus-sg
Port:   80
```

This keeps the Application Load Balancer as the public entry point while the EC2 instance remains protected behind it.
