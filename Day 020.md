# 100 Days of Cloud AWS - Day 020: Create IAM Role for EC2 with Policy Attachment

## Scenario

The Nautilus DevOps team is continuing to configure AWS Identity and Access Management (IAM) resources as part of its cloud migration.

For this task, an **IAM role** must be created for Amazon EC2 and an existing IAM policy must be attached to the role. This allows EC2 to assume the role and obtain the permissions defined by the attached policy without storing long-lived AWS credentials on the instance.

## Requirement

Create an IAM role with the following configuration:

- **IAM Role Name:** `iamrole_john`
- **Trusted Entity Type:** AWS Service
- **Use Case:** EC2
- **Policy:** `iampolicy_john`

## Implementation

### Step 1: Open the IAM Console

1. Sign in to the **AWS Management Console**.
2. Search for:

```text
IAM
```

3. Open **Identity and Access Management (IAM)**.
4. Navigate to:

```text
Access management → Roles
```

5. Click:

```text
Create role
```

### Step 2: Configure the Trusted Entity

Under **Trusted entity type**, select:

```text
AWS service
```

For the **Service or use case**, select:

```text
EC2
```

Choose the EC2 use case and click:

```text
Next
```

This configures the role's trust relationship so that Amazon EC2 can assume the role.

### Step 3: Attach the Required Policy

On the **Add permissions** page, search for:

```text
iampolicy_john
```

Select the checkbox beside:

```text
iampolicy_john
```

Click:

```text
Next
```

> Before attaching an IAM policy in production, review its permissions to confirm that they match the workload's actual requirements.

### Step 4: Configure the Role Name

Enter:

```text
iamrole_john
```

Review the configuration:

```text
Role Name:       iamrole_john
Trusted Entity:  AWS Service
Use Case:        EC2
Policy:          iampolicy_john
```

Click:

```text
Create role
```

## Validation

Navigate to:

```text
IAM → Roles
```

Search for:

```text
iamrole_john
```

Open the role and verify the **Permissions** tab contains:

```text
iampolicy_john
```

Then check the **Trust relationships** tab.

The trust policy should allow the EC2 service to assume the role through:

```text
ec2.amazonaws.com
```

The final relationship should be:

```text
EC2
 │
 │ AssumeRole
 ▼
iamrole_john
 │
 │ Attached Policy
 ▼
iampolicy_john
 │
 ▼
AWS Permissions
```

## Result

✅ IAM role `iamrole_john` created successfully.

✅ Trusted entity configured as an AWS service.

✅ EC2 configured as the role's use case.

✅ Existing policy `iampolicy_john` attached to the role.

✅ Role permissions and trust relationship verified.

✅ Challenge successfully completed and validated.

## Key Takeaway

An **IAM role** differs from an IAM user because a role is designed to be **assumed temporarily** by trusted identities or AWS services.

For an EC2 workload, the relationship is:

```text
EC2 Instance
     │
     ▼
IAM Role
     │
     ▼
IAM Policy
     │
     ▼
AWS Resources
```

Two different IAM concepts are involved:

```text
Trust Policy
    │
    └── WHO can assume the role?
         Example: EC2


Permissions Policy
    │
    └── WHAT can the role do?
         Example: iampolicy_john
```

This distinction is important:

**Trust policy = who can use the role.**

**Permissions policy = what the role can do after it is assumed.**

Using IAM roles for EC2 is preferable to storing long-lived access keys on servers because AWS can provide **temporary credentials** to the instance and automatically rotate them.

In production, combine IAM roles with the **principle of least privilege** so EC2 workloads receive only the permissions required to perform their intended function.
