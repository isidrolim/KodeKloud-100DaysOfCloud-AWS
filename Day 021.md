# 100 Days of Cloud AWS - Day 021: Setting Up an EC2 Instance with an Elastic IP for Application Hosting

## Scenario

The Nautilus DevOps team received a request to deploy a new EC2 instance for hosting an application.

Because the application requires a stable public IP address, an **Elastic IP (EIP)** must also be allocated and associated with the EC2 instance.

## Requirement

Create the following AWS resources:

- **EC2 Instance Name:** `nautilus-ec2`
- **AMI:** Any Linux AMI
- **Instance Type:** `t2.micro`
- **Elastic IP Name:** `nautilus-eip`
- **Region:** `us-east-1`
- Associate the Elastic IP with `nautilus-ec2`.

## Implementation

### Step 1: Open the EC2 Console

1. Sign in to the **AWS Management Console**.
2. Make sure the selected region is:

```text
N. Virginia (us-east-1)
```

3. Search for and open:

```text
EC2
```

4. Navigate to:

```text
Instances → Instances
```

5. Click:

```text
Launch instances
```

### Step 2: Configure the EC2 Instance

Under **Name and tags**, enter:

```text
nautilus-ec2
```

Under **Application and OS Images (AMI)**, select any supported Linux image, such as:

```text
Amazon Linux
```

Under **Instance type**, select:

```text
t2.micro
```

Configure the remaining settings as required by the environment and leave unspecified options at their defaults.

### Step 3: Launch the Instance

Review the configuration:

```text
Instance Name:  nautilus-ec2
AMI:            Linux
Instance Type:  t2.micro
Region:         us-east-1
```

Click:

```text
Launch instance
```

Navigate back to:

```text
EC2 → Instances
```

Wait until `nautilus-ec2` reaches:

```text
Running
```

Ideally, also wait until the instance status checks report:

```text
2/2 checks passed
```

### Step 4: Allocate an Elastic IP

From the EC2 navigation pane, go to:

```text
Network & Security → Elastic IPs
```

Click:

```text
Allocate Elastic IP address
```

Keep the appropriate default settings and click:

```text
Allocate
```

### Step 5: Name the Elastic IP

Select the newly allocated Elastic IP.

Add the following tag:

```text
Key:   Name
Value: nautilus-eip
```

Save the tag.

### Step 6: Associate the Elastic IP

With `nautilus-eip` selected:

1. Click **Actions**.
2. Select:

```text
Associate Elastic IP address
```

3. For **Resource type**, select:

```text
Instance
```

4. Under **Instance**, select:

```text
nautilus-ec2
```

5. Select the instance's private IP address if required.
6. Click:

```text
Associate
```

## Validation

### Verify the EC2 Instance

Navigate to:

```text
EC2 → Instances → nautilus-ec2
```

Verify:

```text
Instance Name:  nautilus-ec2
Instance Type:  t2.micro
Instance State: Running
AMI:            Linux
Region:         us-east-1
```

Confirm that the instance now displays the allocated Elastic IP as its public IPv4 address.

### Verify the Elastic IP

Navigate to:

```text
EC2 → Network & Security → Elastic IPs
```

Select:

```text
nautilus-eip
```

Verify that it is associated with:

```text
nautilus-ec2
```

The final network relationship should be:

```text
Internet
   │
   ▼
nautilus-eip
Elastic IP
   │
   ▼
EC2 Network Interface
   │
   ▼
Private IP
   │
   ▼
nautilus-ec2
t2.micro
```

## Key Takeaway

A standard EC2 public IPv4 address is not intended to provide the same persistent addressing behavior as an **Elastic IP**.

An Elastic IP provides a static public IPv4 address that can be associated with an EC2 instance:

```text
EC2 without EIP

Internet
   │
   ▼
Dynamic Public IPv4
   │
   ▼
EC2


EC2 with EIP

Internet
   │
   ▼
Static Elastic IP
   │
   ▼
EC2
```

This can be useful when an application specifically requires a stable public IP address.

However, having an Elastic IP does **not** automatically make an application reachable:

```text
Elastic IP
     ↓
Internet Gateway / Routing
     ↓
Security Group
     ↓
Network ACL
     ↓
EC2 Network Interface
     ↓
Operating System Firewall
     ↓
Application Listening Port
```

All required layers must permit the traffic.

In production, public IPv4 addresses should be used intentionally because AWS charges for public IPv4 usage. For scalable application architectures, services such as an **Application Load Balancer** are often placed in front of EC2 instances rather than exposing individual application servers directly.
